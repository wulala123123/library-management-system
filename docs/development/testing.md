# 测试与发布检查

本页是项目验证职责、范围选择、证据复用和结束条件的统一入口。发布阶段的耗时、维护窗口与退出路径见[发布验证与维护时间](../operations/release-validation.md)。

## 验证职责

- 执行代理负责选择必要检查、完成技术验证、定位失败和补充受影响的回归，并提供实际结果及证据。不能把运行命令、分析日志或判断技术正确性的工作转交用户。
- 使用经理流程时，经理按交付条件和实际风险验收，直接复用有效证据；普通独立任务由执行代理完成核验，不固定增加审查代理或再跑一遍全部测试。
- 需要用户决定业务规则、功能采用，或用户明确保留最终验收权时，先完成技术核验，再提交简短可操作的业务确认项。用户试用不替代技术验证；未要求用户亲自验收时，不自行增加“等待用户再测一遍”的完成门槛。

## 开始前确定范围和完成标准

普通小修在聊天中简要说明，复杂任务沿用当前任务或活动计划，明确以下内容，不另建重复台账，也不为例行技术选择增加确认步骤：

1. **目标与范围**：本次交付什么，涉及哪些模块和共享代码，哪些事项留待后续。
2. **完成标准**：用可观察的业务结果和必要技术条件说明怎样算完成，区分实现、已验证和已上线。
3. **必要验证**：每组检查对应的风险、执行环境和通过条件；不能只写“全部验证”。
4. **可复用结果**：已有证据入口、适用的源码/依赖/配置/数据条件，以及本次需要补的差异。
5. **工作量与耗时**：预计检查数量和执行时间；逐书、逐会员或逐角色循环先按实际规模计算，不能以小夹具速度推断完整运行时间。

验证覆盖由本次影响和具体风险决定。数据写入、金额、库存、身份、权限、迁移和共享基础代码变化扩大相应验证；纯文档和低风险局部改动采用下述定向入口。用户要求“验证”或“继续推进”，不自动扩大为历次全部功能重新验收。

## 复用证据与失败处理

1. **先复用再补缺口。** 核对相关源码、依赖、配置、环境及数据条件后复用已有结果；候选有变化时判断哪些证明失效。换聊天、接手任务或上下文恢复本身不构成重跑理由。发布目标提交仍须满足完整 Verify 要求。
2. **先定位失败类别。** 区分产品缺陷、测试夹具/断言错误、验证工具缺陷和环境问题，保留原失败。修正后运行能证明修复及相关风险的检查；有具体共享影响才扩大范围，不能通过放宽业务断言或忽略差异获得通过。
3. **工具先独立验证。** 读取、传输、比较或等待工具出现问题时，先用小型合成用例和必要现场探针修准工具，再补受影响的业务检查。工具改动不自动使全部产品测试失效；其影响到的来源绑定、实际环境或恢复证明仍须重验。
4. **无关问题另记。** 未影响本批完成标准及发布安全的问题记录到原计划的后续事项，不顺手修复并扩展本批。会影响数据安全、权限、兼容性或当前交付的问题必须处理，不能为省时跳过。
5. **扩大检查要有依据。** 新增检查或重做验证工具前说明具体未覆盖风险、已有证据为何不足、预计额外工作量及结束条件。例行必要修复自主完成；明显超出用户目标的工作先提交取舍，不让验收范围在执行中无限增加。

## 结束条件与交付

本批完成标准满足、必要检查通过或已有有效证据覆盖、没有影响交付的未决问题时，立即整理结果并交付。阶段任务有尚未实现的部分时按本批范围报告，不扩大完成声明。新增复审或另一套验收工具必须对应具体剩余风险，不能仅为“再保险”持续增加验证层次。

交付说明本次改动、实际验证结果、复用依据、未运行项及其影响、剩余事项和线上生效状态。缺失的必需证据继续补齐；可由执行者完成的工作不留给用户搬运。进展应给出当前阶段、总量/剩余量和预计耗时，仅累计响应数不表示接近完成。

## 本地检查

```bash
python3 scripts/check_docs.py
git diff --check
python3 -B scripts/test_release_validation_plan.py
mvn -B -ntp -f backend/pom.xml verify
pnpm --dir frontend test
pnpm --dir frontend build
pnpm --dir frontend audit --audit-level=high
```

按变更范围选择检查。纯文档修改运行文档检查和差异检查；发布文档路径或打包入口变化时，另核对分发包内容。前端 build 包含完整类型检查。

`scripts/release_validation_plan.py`提供未改模块的确定性代表项选择及按实测成本计算维护预算的纯工具；覆盖类别超出上限时拒绝截断，未知耗时拒绝当作零。其预算结果只说明时间条件，不授权生产操作；本批业务检查、完整数据保全、备份恢复和发布资格须另外满足。对应定向测试已接入 Verify 的文档与工具检查步骤。

## 隔离要求

- 后端快速测试默认使用 H2。设置 `MYSQL_TEST_URL` 后执行真实 MySQL 用例，目标只能是专用、可丢弃的 `library_repair_tests`；账号和密码分别使用 `MYSQL_TEST_USER`、`MYSQL_TEST_PASSWORD`。
- 导入试验只使用脚本允许的独立 `library_transfer_trial_*` 数据库。
- Linux 隔离主机可设置 `CI_NGINX_HTTP=true` 验证生产 Nginx 路由、上传边界和真实 HTTP 流程。
- 测试数据使用合成样例，真实会员资料和财务快照不进入 CI。跳过用例、未运行检查及失败结果如实记录。

## 完整发布门槛

[Verify 工作流](../../.github/workflows/verify.yml)验证后端安全、升级和并发，迁入事务，前端安装、类型、测试与构建，依赖审计，Shell 运维以及实际容器更新、回退和备份恢复。

```bash
python3 scripts/package_release.py vX.Y.Z
# 只在全新隔离 Docker 主机运行
LIBRARY_ACCEPTANCE=1 bash scripts/container-acceptance.sh dist/library-management-system-vX.Y.Z.zip
```

产物在 `dist/`；只有通过目标提交 Verify 的 `verified-distribution` 及配套校验文件用于生产。分发包的公开文档随目录自动收集，凭据与私有运行数据保持排除。

发布前按[发布验证与维护时间](../operations/release-validation.md)区分隔离回归、完整数据保全与正式切换检查，测定真实规模工作量和耗时。沿用旧工具时审查重复查询及环境读取成本；完整 CI 不因维护预算缩减。

## 文档检查范围

文档检查验证固定入口、目录索引可达性、本地链接与标题片段、活动文件命名、长度边界和任务编号唯一性。增加文件、拆分主题或归档时在本地运行，Verify 同步执行。
