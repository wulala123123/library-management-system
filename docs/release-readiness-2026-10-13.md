# 修复计划复审与部署判断

2026 年 10 月 13 日复审结论：**可以进入隔离 Docker 验收，暂不具备正式部署放行条件。** 原计划仍为 45/52 项完成、7 项待运行验收。没有部署到服务器，也没有修改服务器现有服务。

本次核查认证、数据库迁移、库存事务、前端接口、发布包、运维脚本和 CI。核心安全及借还逻辑未发现新的明确阻断问题；这不代表已完成全部功能、负载或生产容器验证。

## 发现与补修

| 问题 | 后果 | 处理 |
| --- | --- | --- |
| Windows SHA256 文件使用 CRLF | Linux 校验把回车当成文件名的一部分，原候选包部署失败 | 强制 LF；新包使用 GNU `sha256sum -c` 验证 |
| Compose 未传入 `LEGACY_BASELINE_VERSION` | 按文档配置后容器仍拒绝旧库升级 | 补齐 Compose 和环境示例；增加原 SQL 文件的 MySQL 升级用例 |
| 停服后才安装备份退出处理 | 部分停服或备份失败可能留下停止的服务 | 停服前安装处理，失败恢复服务并保留非零退出状态 |
| 备份恢复服务只执行 `start` | 无法确认服务恢复成功 | 改为 `up --wait`，恢复失败时报告错误 |
| 恢复不核对应用版本，版本文件无校验 | 错误版本或损坏记录可能被用于恢复 | 版本文件加入校验；要求从对应版本运行恢复脚本 |
| 恢复项目可复用正式代理别名 | 可能影响正式 `library-web` 上游解析 | 恢复环境存在 `use-sub2api` 标记时拒绝启动 |
| 失败更新留下目录后不能重试 | 修正配置或外部故障后仍被版本检查阻止 | 允许相同校验和的非当前版本重试，仍禁止替换不同内容 |
| 缺少 `.env` 时解压后返回成功 | 自动化可能把未启动安装当成部署成功 | 保留示例并返回失败，要求配置后重跑 |

新增 `scripts/operations.test.sh` 覆盖 13 个正常及失败场景并加入 Verify。它使用模拟 Docker 命令检查控制流程，**不能代替真实容器、备份内容或健康检查验收**。

## 上线前门槛

1. 在全新隔离 Docker 主机运行 Verify 或 `scripts/container-acceptance.sh`，取得首次启动、Nginx 文件代理、重建持久化、更新、坏 JAR 回退、备份及独立恢复的实际成功记录。
2. 补齐生产配置、MySQL、Nginx 下管理员及读者登录、采购、续借、文件限额的端到端验收。当前容器 smoke 使用隔离测试密钥签发令牌验证业务及文件路径，未验证容器内验证码登录；生产 HTTP 登录和限额由 Maven 用例验证。
3. 部署时核对目标服务器网络、端口、代理 IP、域名和独立密钥。接管旧库前停写备份，在隔离环境核对真实结构并验证上传目录迁移；表/列集合检查不足以认可自定义结构。
4. 通过后再勾选剩余 7 项并安排上线。回退目标必须是已验证兼容且安全的版本。
