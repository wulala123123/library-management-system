# 数据库迁移与旧库接管

生产使用 Flyway，唯一建表来源是 `backend/src/main/resources/db/migration`。V1 为六张基础表，V2 为扩展模块，V3 添加认证版本、审计表、采购串行锁和库存约束，V4 承接实体册、来源档案和会员原权益。迁移历史保存在 `flyway_schema_history`，重启不重复执行已完成迁移。

V5 增加统一会员版本、档案补充列、多宝宝、资料审计及精确卡号历史占用。升级前只读检查历史非空卡号按二进制值是否重复；重复须核实来源，迁移不清理或合并记录。V1–V4 保留原字节；升级不重算既有日期、次数及金额。

新库由数据源指定库名，迁移不执行 `CREATE DATABASE` 或 `USE library_db`。MySQL 容器创建数据库及两个独立账号：`library_app` 只有读写数据的权限，`library_migrator` 负责模式迁移。应用运行时数据源使用前者，启动迁移使用后者。迁移凭据也属于敏感配置，不能公开或返回给客户端。

H2 仅用于快速回归，字段来自同一生产 DDL 的兼容转换。MySQL 用例另外验证全部实体列、旧库升级、并发库存和权限；H2 不代替这些测试。

## 旧库升级

1. 停止旧应用写入并备份数据库和旧上传目录。
2. 检查表、列、类型、索引、约束和自定义触发器。原 `backend/sql/init.sql` 对应基础版本 1；在其上执行原扩展脚本对应版本 2。两个 SQL 文件保留作旧版开发样例，禁止用它们初始化新生产库。
3. 只有确认结构匹配时，首次升级设置 `LEGACY_BASELINE_VERSION=1` 或 `2`。程序先检查表集合、字段集合，未知表或字段会拒绝接管。这个检查不能代替人工核对字段类型、索引及本地自定义改动。
4. 启动新应用，记录基线后执行剩余迁移。去掉临时的基线变量；之后使用正常的 Flyway 验证与迁移。
5. 验证账号密码、图书、借阅和库存；复制原上传文件到新的上传卷，不要删除旧目录直到恢复演练完成。

生产 `baseline-on-migrate` 始终为 false，不会自动跳过未知结构。原库若包含额外日志表、认证字段或个人修改，应制定相应增量迁移，不能强行设置基线来掩盖差异。已有弱密码或演示账号不会被迁移覆盖，应通过管理员操作处理。

## 后续开发

新增结构使用高于当前最大版本的迁移文件，不修改已执行内容。先保证前后两版都能使用新增字段，下一阶段再处理删除字段。每次改实体同时核对生产迁移、H2 脚本和真实 MySQL 用例。当前正式发布门槛包含容器及恢复演练，见[部署说明](deployment.md)。来源数据操作另见[数据承接](data-transfer.md)。
