# 图书馆管理系统修复计划

依据 2026 年 10 月 13 日的项目检查，先修复账号安全、数据库和借还业务，再完善发布流程。目标是形成一个可测试、可更新、可回退的版本，为后续功能开发提供稳定基础。

当前尚未部署图书馆项目，服务器已有服务没有变更。账号、数据库、业务和前端修复已完成本地验收，部署与发布代码已改写；完整容器演练仍待运行。逐项状态和证据见 [修复记录](repair-results-2026-10-13.md)。检查依据见 [项目检查报告](project-review-2026-10-13.md)。

## 修复范围和实施顺序

| 阶段 | 优先级 | 主要工作 | 完成标准 |
| --- | --- | --- | --- |
| 1 账号安全 | 最高 | 关闭不安全找回密码，修复管理员初始化、JWT 撤销、验证码，补齐相关数据库迁移 | 账号接管和旧令牌越权用例全部被阻止 |
| 2 生产数据库和事务 | 高 | 完整版本迁移、演示数据隔离、实体字段核对、业务与日志事务 | 空 MySQL 可初始化，旧库可升级，重启不改密码、不重复造数据 |
| 3 借还和采购 | 高 | 并发库存、逾期保护、借阅码流程、重复核销和已有 ISBN 入库 | 真实 MySQL 并发测试通过，库存与借阅记录一致 |
| 4 前端类型和依赖 | 高 | 修复 84 处类型错误，统一 API 类型，处理依赖告警，加入核心页面测试 | 类型检查为 0 错误，前后端契约和构建验证通过 |
| 5 部署与持续发布 | 高 | Nginx 路由、文件持久化、统一产物、更新备份和 CI | 解压后的发布包可在隔离环境运行，更新后数据和文件保留 |
| 6 完整验收和交接 | 高 | 核心流程回归、首次安装与升级演练、文档和问题闭环 | 所有阻断问题关闭，形成可部署产物和验收记录 |

阶段 1 先搭建迁移机制并增加认证必需字段，阶段 2 完善全部业务表和升级路径；不维护两套互相独立的生产建表流程。阶段 3 依赖数据库修复，阶段 4 的 API 类型要与阶段 1、3 的接口变更同步，阶段 5、6 验证最终产物。

每阶段拆成可独立审查的变更，记录修改文件、行为变化、测试结果和未解决项。涉及数据库的变更保留升级脚本，禁止依赖删库重建来通过验收。

## 第一阶段 账号安全

主要涉及认证控制器、用户服务、JWT 组件、验证码组件、管理员初始化器、登录页面和相关配置。

- [x] 关闭当前匿名密码重置接口，并关闭前端未实现的找回密码入口。保留受权限控制的管理员重置功能；真实短信或邮件验证作为后续独立功能接入。
- [x] 删除启动时覆盖管理员密码的逻辑。仅在没有管理员账号时，通过明确配置创建初始管理员；重启不得修改已有密码，生产环境不使用默认密码，不将明文密码写入日志。
- [x] 引入认证需要的数据库迁移，为用户增加令牌版本字段，JWT 签发时携带该版本。
- [x] 认证时查询当前账号，检查删除标记、启用状态、当前角色和令牌版本。修改密码、禁用、删除、变更角色时更新版本，使旧令牌失效；无版本的历史令牌要求重新登录。
- [x] 将验证码参数加入登录请求，在后端登录流程中校验并消费。前端去掉先验证再登录的分离流程；验证码缺失、错误、过期和重放均不能登录。
- [x] 保留登录限流，明确可信代理来源，避免任意客户端请求头控制限流身份。生产 JWT 密钥必须显式配置，缺失或不符合要求时启动失败。
- [x] 将首轮临时验证中的安全场景转为仓库内的回归测试，并更新原有登录测试的验证码输入。

验收用例：

1. 匿名请求无法取得密码重置验证码，也无法修改账号密码。
2. 管理员修改密码后重新执行初始化、重启应用，仍使用新密码登录。
3. 修改密码、禁用、删除、降权后，原管理员令牌无法访问管理接口。
4. 缺少、错误、过期或重复使用验证码时登录失败；合法输入可正常登录。
5. 生产环境缺少 JWT 密钥或首次管理员凭据时不会静默使用公共默认值。

## 第二阶段 生产数据库和事务

主要涉及数据库脚本、实体、Mapper、用户管理和规范化服务、测试配置及生产配置。

- [x] 使用统一的版本迁移机制管理基础表、扩展表和后续变更，明确迁移历史与启动顺序。
- [x] 补齐 `permission_log`、`book_normalize_log`；逐一核对所有实体使用的字段、默认值、索引和逻辑删除标记。
- [x] 核对 H2 测试结构与 MySQL 结构。现有测试脚本也存在字段差异，不能直接复制为生产脚本；数据库特有约束在 MySQL 测试中验证。
- [x] 将演示账号、联系方式、样例图书和真实初始化分离。生产仅创建必要基础数据，测试继续使用独立、可重复生成的样例数据。
- [x] 将数据库选择交给数据源和迁移配置，处理脚本硬编码 `USE library_db`，确保建表与应用连接的是同一个数据库。
- [x] 新库执行完整初始化；已有本地数据库先检查结构，再明确选择基线和升级脚本，避免自动将未知结构标记为已迁移。
- [x] 将用户变更与权限日志、图书规范化与记录写入放在合理事务内。日志失败不得留下接口报失败但业务已完成的结果，业务失败也不留下虚假的成功日志。
- [x] 明确生产应用普通数据库账号与迁移账号的权限。既有方案不要求增加 Redis。

验收用例：

1. 空 MySQL 8 数据库启动后全部模块能查询，不出现缺表或缺字段。
2. 从原基础库和原扩展库升级后，用户、密码、图书和借阅记录保持一致。
3. 重新启动、重复运行迁移，不重复创建数据，不覆盖密码。
4. 人为制造审计记录写入失败，业务操作正确回滚；业务操作失败不留下成功日志。

## 第三阶段 借还和采购

主要涉及借阅服务、借阅码服务、图书和用户删除保护、采购服务、Mapper，以及目录与借阅码页面。

### 库存与状态

- [x] 将“未归还”统一定义为 `BORROWING` 与 `OVERDUE`，用于借阅上限、重复借阅、用户删除和图书删除保护。
- [x] 使用数据库条件更新或行锁保护库存变化；明确固定加锁顺序，并检查更新影响行数。库存扣减、借阅记录创建和借阅码消费必须共同提交或回滚。
- [x] 归还、续借、核销和采购入库采用有条件的状态转换，保证重复请求和并发请求不会重复改变库存或突破次数限制。
- [x] 借阅上限与重复借阅校验必须在并发请求下仍然成立，不能只锁图书而忽略同一个用户同时借多本书的情况。
- [x] 维护 `0 <= 可借库存 <= 总库存`，修改总库存不得破坏未归还数量；统计口径包含逾期未还记录。

### 借阅码的建议业务流程

已采用：目录点击生成借阅码，核销成功时创建借阅记录并扣减库存。该实现已经通过 MySQL 并发核销和页面测试。

- [x] 目录和详情页只生成码，提示“已生成借阅码”，避免提前显示“借阅成功”。
- [x] 未核销前不扣库存、不产生借阅记录；码不代表已预留库存，核销时重新检查可借数量和用户状态。
- [x] 核销校验所属用户、有效期和状态，一次只创建一条借阅记录；库存不足时返回明确结果，不留下部分成功数据。
- [x] 保留管理员直接办理借阅的入口，使其与借阅码核销共用借阅规则。
- [x] 已选择核销时完成借阅，保留统一语义；若后续改变规则，应同步修改目录、码与记录的关系。

### 采购入库

- [x] 相同 ISBN 的补购累加已有图书库存，不重复插入唯一 ISBN。
- [x] 新 ISBN 正常建档；明确空 ISBN 的处理与同一 ISBN 元数据冲突的校验。
- [x] 已入库数量、图书库存和入库流水在同一事务提交，防止采购单重复或并发入库。

验收用例：

1. 只有最后一册库存时，多个用户同时借阅，恰好一个成功，库存为 0。
2. 同一用户同时申请多本书，不突破借阅上限；同一本未还书不能重复借阅。
3. 同一记录同时归还多次，只增加一册；不同记录并发归还时每册都计入库存。
4. 逾期未还记录阻止重复借阅以及关联用户、图书的删除。
5. 生成码不扣库存；同一码重复或并发核销只产生一条借阅记录。
6. 已有 ISBN 的采购入库准确累加库存，重复入库不累加第二次。

这些用例在真实 MySQL 中验证。H2 保留用于快速测试，但不作为库存并发和 MySQL 约束的唯一证据。

## 第四阶段 前端类型和依赖

主要涉及请求封装、全部 API 类型、受影响页面、包管理配置和前端测试。

- [x] 修复请求参数与 DTO 的类型冲突，为各接口明确返回类型；正确支持无请求体、表单和文件上传，不通过大面积改为 `any` 掩盖错误。
- [x] 修复不存在的字段、错误导入和页面中未知类型的访问；以首轮 84 处错误为基线，将最终完整 Vue 类型检查降至 0 错误。
- [x] 添加 `typecheck` 脚本，使类型检查成为构建和发布的必要步骤。
- [x] 固定并验证 Node、pnpm 和锁文件组合，明确必要依赖构建脚本的允许策略，本地和 CI 使用相同安装方式。
- [x] 按实际使用路径处理前端 33 条依赖告警，分别记录版本、受影响场景、升级结果和残余风险；补做后端依赖审计并处理发现的问题。
- [x] 每组依赖升级单独验证，避免在同一次变更中混合大量业务修复和跨大版本迁移。
- [x] 增加登录、借阅码生成核销、归还和采购相关页面的关键流程测试。

验收标准：完整 Vue 类型检查为 0 错误；前端和后端生产构建均通过；前后端请求参数与响应格式一致；依赖审计中与实际运行相关的高风险问题已处理或明确阻断发布。

## 第五阶段 部署与持续发布

主要涉及 Dockerfile、Compose、Nginx、部署脚本、GitHub Actions 和环境变量示例。

- [ ] 修复 `/api/` 与 `/uploads/` 的 Nginx 匹配优先级，验证生产代理下的头像、封面和资源访问。
- [ ] 统一上传路径配置，独立持久化上传文件、数据库和日志。现有已跟踪上传图片先核对用途，再整理为演示资源或迁出运行目录。
- [ ] 统一前端提示、代理和后端的文件大小限制。暂按现有资源接口需求支持 50MB 资源文件，头像和封面仍按各自的较小限制校验，并实际测试临界大小。
- [ ] 建立唯一发布目录规范，使 JAR、前端产物、迁移脚本、Compose、Nginx 配置和文档相互匹配。
- [x] 修复 ZIP 解压路径和版本目录处理；更新只替换代码或镜像，保留环境变量与持久化数据。
- [x] 按当前项目实际端口和健康检查验证启动，不固定检查其他服务的 80 或 8080，也不以固定等待 10 秒代替就绪检查。
- [ ] CI 同时验证后端测试、前端类型检查与构建、MySQL 初始化与升级、发布包内容和容器运行。
- [x] Release 使用仓库锁文件，发布前完成检查，移除删除既有标签和 Release 的更新方式；发布失败保留已有有效版本。
- [x] 明确数据库和上传文件备份、恢复、应用回退的步骤；数据库迁移采用兼容上一版应用的策略，不能假定回退镜像等于回退数据库。
- [x] 将已有 sub2api 部署模板与最终产物统一，继续采用独立项目网络和数据库、现有 `proxy` 网络，以及本机试运行端口 `18080`。

验收用例：

1. 在隔离环境中使用解压后的发布包启动项目，全部健康检查通过。
2. 上传头像、封面与资源文件后替换容器，文件仍存在并能访问。
3. 保留旧数据库执行应用升级，数据完整，迁移只执行一次。
4. 健康检查失败时能够明确报错并恢复上一版应用；备份能恢复到独立环境。
5. 运行配置不会占用现有 sub2api 服务端口，数据库和后端端口不直接公开。

该阶段只修复并验证部署能力。安装到 sub2api、修改代理或 DNS、发布到公网以及服务器系统升级均作为后续部署工作处理。

## 首批实现和完成条件

第一批以关闭账号接管入口、保留已修改密码、撤销旧权限和补齐认证迁移为交付范围。随后依次完成全部业务迁移、借还与采购、前端与依赖、发布和验收。已经明确的日常实现选择按本计划推进；借阅码语义等会影响用户操作的选择在变更说明中单独列出。

进入部署阶段前，必须满足：账号安全回归通过、真实 MySQL 核心业务验证通过、类型检查为 0 错误、发布包与容器验收通过、更新和备份恢复步骤可执行。最终部署时间与服务器系统升级另行安排。
